  - 混合架构（确定性流水线 + LLM Agent）✓：规则模板引擎 internal/config/rules、文件捆绑分组、agent 工具循环 internal/llmloop 均在源码可指认；

- **小样实测（真实跑通，非纸面）**：自建 Java 仓库埋 3 个已知缺陷（静态共享 SimpleDateFormat 线程不安全 L7、`cache.get(key).toUpperCase()` NPE L15、FileInputStream 未关闭 L18-20）。

  - **结论：单次检出率有波动（agent 循环非确定性），与官方 precision>recall 取舍一致；不能把 3/3 当稳定能力宣传。**

## 二、做得对的

1. **按 assignment 顺序执行：先核实再试用**。GitHub API 拿许可证/热度硬数据，浅克隆读源码核对架构宣传，转发摘要只当线索不当事实——一次性抓出 npm 包名错误。
2. **试用样本设计成可机械判定**：埋已知缺陷再评审，检出率/行号/误报都能逐条核对，不靠"感觉评得好"。
3. **接入走官方路径**：配置用 `ocr config set` 官方 CLI（非手写 JSON）；独立验证时刻意清除环境变量，证明生效的是配置文件而非环境残留。
4. **两次实跑差异如实上报并写进常驻文档**，没有只报好看的第一轮；应对建议（关键文件人工确认/复跑取并集）进了技能。
5. **docs 门禁拦截时按规范补官方文档阅读与回执后重试**，未绕过门禁（第六节机制按设计工作）。

## 三、犯过的错 / 差点踩的坑

1. **先猜包名后读 README，顺序反了**：`npm view open-code-review` 404 后又猜 `@alibaba-group/ocr`（又 404），共浪费 2 次查询；README 安装段一步即给正确答案。核实类任务应"权威源先行"。
2. **后台长任务期间反复轮询**：评审跑着时 `job_output` 轮询约 8 次而非结束回合等完成唤醒，白耗多个回合（规范本说"勿 poll"）。
3. **单次结果险些当稳定结论**：第一轮报告写"3/3 全检出"未标明是单次抽样；第二轮就漏了 1 个。若接入轮没有复跑，非确定性这个关键限制就被漏掉了。

## 四、如果重来会怎么做

1. 权威源先行：动手前先读官方 README 的安装/基准段，二手摘要一律待核实。
2. 后台任务一律结束回合等唤醒，不轮询。
3. 小样试用直接设计为**同样本跑 2 次**，第一轮就暴露非确定性，不等接入轮补。
4. 评估通过即当场完成"配置固化 + 独立验证 + 技能归位"三件套（本轮顺序正确，保持）。

## 五、仍未解决 / 后续建议

1. **与通用 agent 同题对照未做**：官方"1/9 token、precision 更高"是自建基准（AACR-Bench），本机未复测，无法独立证实。
2. **检出非确定性无量化**：只有 2 个样本点；如要认真用于把关，建议 10+ 缺陷样本统计检出率与波动。
3. **二进制架构**：npm 装的是 darwin/amd64 包（本机 node 为 x64），若整机为 arm64 则 ocr 走 Rosetta（功能正常，性能略损）；换 arm64 node 重装可解，未做。
4. **CI 接入未配**：GitHub Actions 按官方 docs/cicd 可加（用户未要求）；需要时另立工单。
5. **运行时依赖**：ocr 走本机 harness 代理 127.0.0.1:15721，宿主停机即不可用；要独立于宿主需另配真实 provider key。
